# Published menus and closed-order dispatch

The branch menu draft loads active restaurant catalog dishes automatically. A new draft starts with the catalog; opening Edit on a published menu refreshes catalog dishes/prices, removes catalog dishes now inactive, and retains manually entered dishes. Published offer snapshots never change silently. The editor and row actions are hidden after publication; Edit menu opens them and Cancel restores the published snapshot. There is no separate catalog picker or reload button. Catalog edits require explicit republishing to affect the reusable offer. Existing customer order prices/finances remain unchanged.

Only a customer administrator explicitly closes and sends orders. Automatic 09:30 cutoff stops customer ordering but does not release the kitchen list. Both Merchant UI subscriptions and Rules require days.status=closed plus closedAt and dispatchId. When ordering reopens, Merchant unsubscribes/clears orders and stops fulfillment writes.

closedAt is the first explicit close timestamp, written with serverTimestamp and immutable thereafter. Reopening is allowed through closedAt+15 minutes (inclusive), evaluated by Firestore request.time. All admin paths, including menu edits and the pickup draw, retain it. Closing again requires a new hexadecimal 32-character dispatchId; it does not extend the deadline. Legacy closed days without metadata use cutoffAt as their deadline, and the next explicit Send initializes metadata without resetting that anchor.

merchantFulfillments adds dispatchId. The document must match the current closed day; a new dispatch can only start at accepted, even when the order fingerprint is unchanged. Later steps remain accepted → cooking → ready → delivering → completed, with existing owner/manager/kitchen boundaries and paired immutable events. Cơm Nhà subscribes live and displays Đã nhận đơn, Đang nấu, Sẵn sàng, Đang giao, Hoàn tất. Old dispatch progress is hidden while open or awaiting acceptance of a new list. Earlier paired events remain as history.

Concurrent pickup closers may receive permission-denied when Rules evaluate against the winning dispatch before an SDK conflict retry. This narrow case reads the authoritative server day and only proceeds if the same roster is already validly closed. The final draw transaction still rechecks administrator rights, order versions and immutable draw history.

No new collection, index, OIDC, credential, or environment variable. Publish the complete configured customer firestore.rules before deploying both portals. Public Rules retain the administrator placeholder. Validation includes pre-close read/list denial, tenant and role limits, immutable timestamps, schema/type/size validation, expired/legacy reopening, redispatch isolation, all financial regressions, concurrent pickup draws, and real two-portal browser tests with fictitious data.
